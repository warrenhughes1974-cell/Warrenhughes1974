ITEM 01 — Policies >60 days past due vs lapse days (cutover risk)
Status:     RECOMMENDED
Owner:      Warren / Client ops
Decision:   (pending client accept of approach)
Updated:    2026-07-16
--------------------------------------------------------------------------------

QUESTION
  Should we check for policies more than 60 days past due before go-live, and
  temporarily raise lapse days so those policies do not terminate on day 1?

ANSWER / RECOMMENDATION
  YES — run this check before go-live and temporarily raise lapse grace if any
  premium-paying actives are past the configured lapse days.

  Why:
  - On first live cycle, QLA will compare paid-to / bill-to aging against the
    plan/list lapse-day setting (QuikPlan MLAPSE / QuikList MLAPSEL).
  - If a policy is already past that grace at cutover, it can lapse/terminate
    on day 1 even though LifePRO was still carrying it as active.
  - Safer pattern: set lapse days high enough to cover the worst in-force past-due
    active case for cutover, go live, clean up collections / true lapses, then
    pare lapse days back down to the contractual/business target.

  Pre-go-live checklist:
  1. Count Active (status 22) policies by days past MPAIDTO as of go-live date.
  2. Note max days past due among those actives.
  3. Compare max days to current MLAPSE / MLAPSEL.
  4. If max > configured lapse days → temporarily raise lapse days (plan and/or
     list, whichever drives processing for this book) above that max (add a
     small buffer).
  5. After live and cleanup, reduce lapse days to the permanent value.

SPOT CHECK (Output quikmstr.csv as of 2026-07-16 analysis date)
  Active status 22 population: 2,162
  Past due >60 days (MPAIDTO): 1,715
    61-90:     73
    91-120:   115
    121-180:  837
    181-365:  675
    366+:      15
  Max observed past due (status 22): policy 010849882C, MPAIDTO 20190901 (~2,510 days)
  Current quikplan MLAPSE: all 0 (141 plans) — with 0/short grace, day-1 lapse risk
  is real for a large share of actives if batch lapse runs immediately.

  Note: Exclude RPU/ETI/claim/etc. statuses from this aging check; paid-to can be
  old on those for legitimate reasons and should not drive lapse-day sizing.

ACTION

  [ ] Re-run aging as of actual go-live date (not analysis date)
  [ ] Set temporary MLAPSE / MLAPSEL based on max eligible past-due + buffer
  [ ] Document permanent target lapse days for post-live rollback
  [ ] Calendar a post-live task to pare lapse days down
