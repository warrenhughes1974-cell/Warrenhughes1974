## Headline

1. **L05 is not data-blocked and needs no source request from CSO / New Era.** The earlier conclusion was drawn from the **April** extracts. The current **8/31** extracts contain L05's reserve grid, correctly keyed, and QLAdmin already has those rows keyed to the classes L05 policies carry. L05 has nothing to do with the underwriting-class change.
2. **L14's diagnosis is correct and is now provable from LifePRO's own valuation output**, not merely inferred from how the source grid is tagged.
3. **The L14 plan as written would fix about half the problem.** It omits `QuikNps` (required — it drives `MTABNET`), omits `QuikNff` and four option tables, and its row counts are off by roughly 4×. One revision pass and it is ready.

## Part 1 — L05

### 1.1 The April-extract error

The Discovery and Planning documents concluded "no L05 reserve data exists in the LifePRO source" from:

- `plan_analysis/source_data/rates/Rate_Table_Extract_20260427.csv`
- `plan_analysis/source_data/rates/PAAGERAT_AttainedAge_Rates_Extract_20260428.csv`

Both are from April. `QLA_Migration/Source/` holds the current package, regenerated by New Era on **8/31** (file dates 9/1):

- `PDAGE_AgeDuration_Rates_Extract_20260831.csv` (393 MB)
- `PAAGE_AttainedAge_Rates_Extract_20260831.csv`
- `PAAGERAT_AttainedAge_Rates_Extract_20260831.csv`

There is no `Rate_Table_Extract` in `Source/` at all — the April file is a superseded derivative.

A second error compounded it: the Planning notes read column 2 of PAAGERAT as the UW class. Column 2 is `TYPE_CODE`; the UW class is column 5. So "L05 has PR-class data" was actually "L05 has PR-**type** (premium) data."

### 1.4 The actual defect

Where L05 fails, `MTABNET = 0` — QLAdmin's valuation did not resolve a net premium, **although the row is present in `QuikNps` at the policy's own UW class**:

| Policy | Age | Dur | Cls | `QuikNps[dur]` | `QuikNps[dur−1]` | `MTABNET` | LifePRO reserve |
|---|---:|---:|---|---:|---:|---:|---:|
| 9011096290C | 40 | 32 | PR | 134.76 | 118.94 | **0.00** | 5,963.50 |
| 9011096291C | 40 | 32 | PR | 128.22 | 111.06 | **0.00** | 2,749.75 |
| 9011097702C | 39 | 32 | PR | 111.94 | 97.28 | **0.00** | 9,768.00 |
| 9011100498C | 37 | 32 | PR | 92.08 | 79.66 | **0.00** | 1,965.50 |
| 9011097650C | 28 | 32 | ST | *none* | *none* | **0.00** | 389.75 |

So this is a **net-premium resolution failure inside the valuation**, not a missing rate table and not a UW-class key problem. Note the near-misses: for the four PR policies, `QuikNps[dur−1] × units` lands within 0.3–1.3% of LifePRO's `RV_VALUATION_PREMIUM` (11,894 vs 11,927; 5,553 vs 5,499; 19,456 vs 19,536; 3,983 vs 3,931), where the resolving policies match to the cent — pointing at an age/duration alignment boundary on the attained-age series rather than absent data.

`9011097650C` is the one genuine coverage gap: the ST net-premium strip at age 28 stops at duration 5 and the policy is at duration 32. That is consistent with the source, where the `L05 10Y 95` smoker side carries half the rows of the preferred side (636 vs 1,272). One policy, $389.75.

### 1.5 This explains Jill's "matched some but not all"

The L05 policies that match are exactly the ones that resolved a net premium. The ones that don't are the ones where `MTABNET` came out zero. Nothing about it is class-related: L05's `QuikTvs`/`QuikNps` rows are keyed **PR and ST**, matching its policies (PR=18, ST=2).

### 1.6 Same defect, larger exposure — L01

`5L0110` resolves **0 of 124** policies, a **$169,718** gap, and §1.3 shows the data to value it correctly is already in the package.

### 1.7 Caveat

`docs/Valuation/QuikValf.dbf` is from the **9/2** valuation run; `Output/rates/` is **9/13**. The 9/13 regeneration may already have moved L05/L01. A fresh QuikValf against the current package should be obtained before this diagnosis is locked.

## Part 2 — L14 development readiness

### 2.1 Confirmed, and on stronger evidence than the plan used

The plan inferred class-invariance from the source grid's class tagging. It is provable directly from LifePRO's own valuation output — identical per-unit mean reserves across classes at the same age, duration and gender:

| Age | Dur | Sex | LifePRO per-unit reserve | NT policies | PQ policy |
|---:|---:|---|---:|---|---|
| 62 | 23 | F | **636.23** | 9011230763C (5 u → 3,181.15), 9011232740C (7 u → 4,453.61) | 9011258186C (15 u → 9,543.45) |
| 62 | 24 | F | **659.72** | 9011226092C (15 u → 9,895.80) | 9011227604C (15 u → 9,895.80) |

**LifePRO's L14 reserve genuinely does not vary by underwriting class.** Supporting evidence: in `PDAGE_20260831` the L14 `CV`, `NF`, `NP` and `RV` grids all carry the single class `N`, while only the premium (`PR`) grid carries `N/Q/R/T`. All 37 NT policies currently match LifePRO to the penny, so the rows that exist are right. And `QuikPlUw` already lists all four classes (NT, PQ, PR, ST) for `1L14SC` — only the factor and option rows are missing.

Exposure: **71 valued policies, $940,556** currently sitting at zero (PQ 65 / $894,645; PR 5 / $42,789; ST 1 / $3,121).

### 2.2 Gap 1 — `QuikNps` is missing from the plan and is required

The plan scopes `QuikTvs` + `QuikCvs`. L14's mean reserve also uses the net premium: NT policy `9011209068C` has `MTABNET` = 466.50 = 31.10 (its `QuikNps` value) × 15 units, and `MRESERVE` = `MMEAN` × units = 575.52 × 15 = 8,632.80, matching LifePRO. PQ/PR/ST policies have **no `QuikNps` row**, so `MTABNET` = 0. Replicating only `QuikTvs` leaves `MTABNET` at zero and the reserve still wrong.

Full set of NT-only tables for `1L14SC` in the current package:

| Table | NT rows | Needs PQ/PR/ST |
|---|---:|---:|
| `QuikTvs` | 332 | +996 |
| `QuikNps` | 328 | +984 |
| `QuikCvs` | 332 | +996 |
| `QuikNff` | 324 | +972 |
| `QuikPlTv` | 2 | +6 |
| `QuikPlCv` | 2 | +6 |
| `QuikPlDb` | 2 | +6 |
| `QuikPlDv` | 2 | +6 |
| **Total** | | **+3,972** |

`QuikGps` and `QuikPlGp` already carry all four classes and must not be touched.

### 2.3 Gap 2 — row counts are off by roughly 4×

The plan states ~8,622 `QuikTvs` and ~8,508 `QuikCvs` rows added (≈17,000 total). Those are **source** row counts; the emitted tables are paged ten durations per row. Actual total is **3,972**. Smaller and cleaner than assumed, but the plan's sizing and any validator row-count assertion derived from it would be wrong.

### 2.4 Gap 3 — the plan did not establish that class-keyed rows are the right shape

I tested the alternative: emit one grid at the `UWCLASS=00` default and let QLAdmin fall back. Four plans — `9L01WP`, `901ADB`, `976659`, `996ADB` — have their reserve grid **only** at `00` while their policies carry PR/ST, and all of them value non-zero. That looks like proof of fallback.

It is not. All **31 of 31** of those policies are entirely net-premium driven: `MMEAN` = `MTABNET / (2 × units)` and `MRESERVE` = `MMEAN × units`, under commercial (half-up) rounding, with zero unexplained residual. The `00` reserve grid is never actually read. (Python's banker's rounding made five of them look like genuine residuals; all five are exact half-cents — 0.105, 0.125, 0.145.)

**So fallback to `UWCLASS=00` is unproven, and keying rows to the classes the policies actually carry — the plan's approach — is the only shape the evidence supports.** Correct call, for a reason the plan had not established. Worth recording, because "collapse to 00" is the smaller and more tempting change and it would have failed.

### 2.5 Verdict

**Not quite ready — one revision pass.** The diagnosis is sound and the approach is right. Before development:

1. Add `QuikNps` and `QuikNff` to the replication scope, plus the `QuikPlTv` / `QuikPlCv` / `QuikPlDb` / `QuikPlDv` option rows.
2. Correct the row counts to 3,972 and re-derive the validator assertions.
3. Record §2.1 (identical LifePRO per-unit reserves across classes) as the evidence for class-invariance, replacing the source-tagging inference.
4. Keep `QuikGps` / `QuikPlGp` / `quikridr.MUWCLASS` / all `*VARY*` flags untouched, as the plan already specifies.

Risk remains low: additive only, no existing row is modified, the 37 matching NT policies are untouched, and rollback is deleting the added rows.

## Part 4 — Related finding: two different source paths for rate data

`qla_core/plan_source_paths.py` exposes two separate resolutions, and they disagree:

| Accessor | Resolves to | Current? |
|---|---|---|
| `paagerat_rate_paths()` → `pdage_extract` / `paage_extract` / `paagerat_pr_extract` | `QLA_Migration/Staging/{pdage,paage,paagerat}_dated_merged.csv`, merged from the dated extracts | **Yes** — picks up 8/31 |
| `rate_table_extract()` | `plan_analysis/source_data/rates/Rate_Table_Extract_20260427.csv` | **No** — April, and holds no L05 rows at all |

The rate emit reads the merged staging path, which is why the emitted `QuikNps` values for L05 and L01 reconcile exactly to LifePRO (§1.3). The April file is the one that produced the false "no L05 reserve data exists" reading.

Worth a look, though not part of this issue: `rate_table_extract()` is an input to `quikplan_rate_variation_flags.py` (the `*VARY*` flag derivation, incl. `UWVARYTV`) and to `variation_classification.py`. A source that predates New Era's 8/31 regeneration feeding the flags that decide whether rates vary by underwriting class is a latent staleness path, and it sits right next to Issue #168's subject matter. Recommend raising separately rather than folding it into this fix.

**Note on side effects:** resolving `paagerat_rate_paths()` during this review rebuilt `QLA_Migration/Staging/paage_dated_merged.csv` and `pdage_dated_merged.csv` from the current dated extracts. `QLA_Migration/Staging/` is gitignored (`.gitignore:20`); no tracked file was touched by this review.
